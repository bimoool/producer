## 2. Вывод и выбор основы

**Основа: официальный Supabase-шаблон `with-supabase` (Next.js + Supabase Auth + shadcn/ui)
+ готовые блоки shadcn/ui (`dashboard-01`, `sidebar`, `login`) для интерфейса.**

Почему не Plane/Vikunja/Leantime:
- Их сильная сторона — задачи. Наша ценность — **декларация, гипотезы, прогресс, отчёт**,
  а этого нет ни в одном из них. Всё равно пришлось бы писать эту логику,
  но внутри чужой архитектуры (Django / Go / PHP), под AGPL и с тяжёлой инфраструктурой.
- Задачи + подзадачи + история — это ~3 таблицы и несколько форм. Дешевле написать
  их поверх готовых компонентов, чем поддерживать форк или синхронизацию двух систем.
- Telegram-бот должен работать с той же базой: в нашей схеме это просто
  ещё один route handler того же Next.js-приложения.

Почему не Kiranism-шаблон целиком: он завязан на Clerk (а нам нужен Supabase Auth,
чтобы RLS в БД работала из коробки) и содержит много демо-кода. Берём те же
компоненты напрямую из shadcn CLI — это тот же результат без чистки.

Что используем готовое (не пишем сами):

| Задача | Готовое решение |
|---|---|
| Авторизация, сессии, защита страниц | Supabase Auth + `@supabase/ssr` (из шаблона) |
| БД, миграции, права доступа | Supabase Postgres, Supabase CLI migrations, Row Level Security |
| UI-компоненты | shadcn/ui (Card, Dialog, Sheet, Form, Tabs, Badge, Progress, Sonner…) |
| Дашборд, sidebar, мобильная навигация | shadcn blocks `dashboard-01`, `sidebar-07` |
| Таблицы задач | TanStack Table (через shadcn data-table) |
| Графики прогресса и финансов | Recharts (через shadcn charts) |
| Перетаскивание (позже, порядок задач) | dnd-kit |
| Валидация на сервере и клиенте | zod + react-hook-form |
| Даты и часовой пояс Asia/Yekaterinburg | date-fns + @date-fns/tz |
| Telegram | grammY (webhook-режим) |
| Плановые задачи (уведомления, пятничный отчёт) | Vercel Cron (или Supabase pg_cron) → защищённый route handler |
| Тесты | Vitest (логика) + pgTAP/SQL-тесты или Vitest против локального Postgres (триггеры) |
| ИИ | `@anthropic-ai/sdk`, на этапе 1–4 — интерфейс + заглушка |

Проверенные версии (npm, 09.10.2026): next 16.4.0, @supabase/supabase-js 2.117.3,
@supabase/ssr 0.12.7, grammy 1.46.0, @tanstack/react-table 9.2.8, recharts 3.10.1,
@dnd-kit/core 6.3.1, zod 4.6.5, vitest 5.0.3, supabase CLI 2.120.0 — все MIT.
(Конкретные версии зафиксируем по тем, с которыми совместимы shadcn-блоки.)

Что пишем сами (это и есть продукт):
1. Схема БД, миграции, RLS, триггер неизменности декларации, журнал изменений.
2. Расчёт прогресса (с различием «не подтверждено» ≠ 0).
3. Экраны: дашборд, декларация, цели, задачи (+ «Зачем я это делаю?»), гипотезы,
   эксперименты, проекты, финансы, отчёты, настройки.
4. Генератор пятничного отчёта по строгому шаблону.
5. Логика бота (команды, парсинг «завтра написать клиенту…», подтверждение).
6. Планировщик уведомлений с дедупликацией.
7. Слой ИИ-планирования (предложение → подтверждение → запись).

## 3. Архитектура

```
             ┌──────────────── Vercel (один Next.js-проект) ────────────────┐
 Браузер ──▶ │  App Router (RSC + Server Actions)   UI: shadcn/ui           │
 (ПК/телефон)│  lib/domain/*  ← чистая бизнес-логика (тестируется Vitest)   │
             │  /api/telegram  ← grammY webhook (проверка secret + user ID) │
 Telegram ──▶│  /api/cron/*    ← уведомления, пятничный отчёт (CRON_SECRET) │
             │  lib/ai/*       ← интерфейс AiPlanner (заглушка → Claude)    │
             └──────────────────────────────┬──────────────────────────────┘
                                            │ supabase-js (RLS / service role для бота и cron)
                                   ┌────────▼─────────┐
                                   │ Supabase Postgres │ миграции, RLS, триггеры
                                   │ Supabase Auth     │ вход по email, регистрация выключена
                                   └───────────────────┘
```

Принципы:
- Один репозиторий, одно приложение, одна БД. Без микросервисов, очередей и Kubernetes.
- Все записи проходят через серверные действия с zod-валидацией; RLS — второй рубеж.
- Неизменность декларации гарантирует **сама БД** (триггер), а не только UI/API.
- Бот и cron используют те же функции из `lib/domain`, что и сайт.

## 4. Модель данных (миграции Supabase)

Все таблицы имеют `user_id` (RLS: `user_id = auth.uid()`), `created_at`, `updated_at`.

| Таблица | Ключевые поля | Примечания |
|---|---|---|
| `projects` | title, description, status | «Контент-завод ББФ», «Спортивный блог Веры», … |
| `goals` | title, description, category, project_id?, target_value?, current_value?, unit?, deadline?, status | `current_value = NULL` → «Прогресс не подтверждён» |
| `declarations` | title, declared_on, cycle_end?, price_of_word, reward, financial_hypothesis, locked_at | Шапка декларации (цена слова, награда, финансовая гипотеза) |
| `declaration_items` | declaration_id, position, original_text, target_value, unit, completion_criteria, deadline?, status, current_value?, locked_at | **Триггер**: после `locked_at` запрещено менять original_text, target_value, unit, completion_criteria и удалять строку. Status и current_value — можно |
| `progress_updates` | goal_id XOR declaration_item_id, value, delta, note, source (web/telegram), created_at | Append-only история прогресса (UPDATE/DELETE запрещены) |
| `hypotheses` | project_id?, goal_id?, statement, expected_result, success_criteria, status (draft/active/confirmed/refuted/needs_decision), conclusion | |
| `experiments` | hypothesis_id, title, scenario, started_at, ended_at, result, conclusion, next_actions | Сценарии/результаты/выводы для «тестов контент-завода» |
| `metrics` | title, unit, goal_id? / hypothesis_id? / experiment_id?, target_value? | |
| `metric_values` | metric_id, value, measured_at, note | Значения метрик во времени |
| `tasks` | title, description, project_id?, goal_id?, hypothesis_id?, parent_task_id?, status, priority, due_date?, estimated_hours?, actual_hours?, result, completed_at | Связь с целью **не обязательна** |
| `task_comments` | task_id, body | |
| `activity_log` | entity_type, entity_id, action, changes (jsonb diff), source, created_at | Заполняется триггерами на всех основных таблицах. `TASK_EVENT` = представление `task_events` поверх `activity_log` (не дублируем таблицу) |
| `finance_entries` | kind (revenue/expense), status (**actual / expected / potential**), amount, deals_count, occurred_on, business (основной/доп.), note | Реальное, ожидаемое и потенциальное никогда не суммируются вместе. Средний чек = выручка(actual) / оплаченные сделки; при 0 сделок — «—» |
| `weekly_reports` | week_number, period_start, period_end, status (draft/final), content (markdown), manual_fields (jsonb: фокус, инсайт, состояние, вопросы…), generated_at | История отчётов |
| `notification_settings` | kind, enabled, time_local | Часовой пояс Asia/Yekaterinburg |
| `notification_log` | kind, entity_id?, dedupe_key **UNIQUE**, sent_at, channel, payload | Дедупликация на уровне БД |
| `telegram_pending` | chat_id, draft (jsonb), expires_at | Черновик задачи из сообщения до подтверждения |
| `ai_suggestions` | prompt, plan (jsonb), status (proposed/accepted/rejected) | Этап 5; задачи создаются только при `accepted` |

Итого ~17 таблиц; каждая соответствует сущности из ТЗ или требованию
(история, дедупликация, подтверждение). Лишних нет.

## 5. Начальные данные (seed)

Декларация от 30.09.2026, `locked_at` = момент фиксации:

| # | original_text | target | Критерий |
|---|---|---|---|
| 1 | Провести 15 кастдевов по проекту «Спортивный блог Веры» | 15 кастдевов | 15 заполненных кастдевов |
| 2 | Провести 3 встречи по упаковке и запуску YouTube-канала | 3 встречи | Отчёт по проведённым встречам и конверсии в сделку |
| 3 | Снять пилотный выпуск YouTube в творческий проект | 1 выпуск | Опубликованный выпуск на YouTube-канале |

- Финансовая гипотеза: «Получить 150 000–300 000 ₽ чистыми, если проверяемые гипотезы сработают» —
  хранится как текст гипотезы, **не** как цель/обещанный результат.
- Цена слова: 20 000 ₽. Награда: покупка футболки и рубашки в «Табу».
- `current_value = NULL` у всех трёх → «Прогресс не подтверждён».
- Вне декларации: задачи «Пройти курс «Выбор ниши»» и «Пройти курс «Выбор Мишы»» (буквально),
  проект «Контент-завод ББФ», цель «Провести тесты контент-завода ББФ» без метрик/сроков.

## 6. План MVP по этапам

| Этап | Содержание | Как проверяю |
|---|---|---|
| **1** | Шаблон with-supabase + shadcn; вход; миграции и RLS; декларация (+ триггер); цели; проекты; задачи, подзадачи, связи, комментарии, «Зачем я это делаю?»; дашборд (декларация, цели, Сегодня/Неделя/Просрочено/Заблокировано, последние изменения); история; мобильная навигация; seed | Vitest (прогресс, даты/TZ, группировка задач); SQL-тесты против локального Postgres (неизменность декларации, append-only история, RLS); сборка + Playwright-прогон основных сценариев на десктопе и мобильной ширине |
| **2** | Гипотезы, эксперименты, метрики, финансы (actual/expected/potential, средний чек) | Тесты расчётов, пустые данные, деление на ноль |
| **3** | Генератор пятничного отчёта по шаблону, история, «Скопировать отчёт», финансы только в последнем отчёте месяца, «Требует подтверждения» | Снапшот-тесты отчёта на пустых и заполненных данных |
| **4** | grammY-бот (/today /week /goals /report /add, свободный текст → подтверждение), allowlist user ID, уведомления с дедупликацией, cron | Юнит-тесты парсера и дедупликации; живая проверка — после деплоя (здесь Telegram API закрыт) |
| **5** | Claude: декомпозиция цели → план → подтверждение; анализ гипотез; голос (Whisper/др.) | Тесты: ИИ не может писать в декларацию/завершать задачи/удалять |

Каждый этап — отдельные коммиты, запуск, тесты, короткий отчёт.
